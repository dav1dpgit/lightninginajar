# Lightning in a Jar

A bitcoin wallet that runs in the browser: on-chain plus Lightning, the Lightning side built on LDK compiled to WebAssembly, connected to a Lightning service provider (LSP) through the open LIJOX registry. Live at https://lightninginajar.xyz. This repository is the wallet — the engine, the page, the build that produces what is served, and the design records.

**Status: pre-release. No third-party security audit. Read the whole of this file before funding it.**

## What it is

- **Pure Lightning, no side-chain.** Channels are the wallet's own LDK channels with its LSP; there is no Spark/Ark-style shared-custody construction. On-chain funds sit at ordinary BIP84 addresses.
- **Your bitcoin key is your Lightning key.** Everything derives from the 12 words. On-chain funds are recoverable in any BIP84 wallet; cooperative and force closes pay the wallet's side straight to its own m/84 address. A channel closed by force shows when its balance is available: the number of blocks, counted down (since page v1182).
- **An open LSP market (LIJOX).** Any node operator can run the adapter, register, and serve any wallet that speaks the standard; wallets choose and switch providers. Since page v1189 (engine v394, 2026-11-27) a wallet that switches can move its Lightning balance to the new provider over Lightning — one payment, out of the old channel, through the old provider, into a channel the new provider opens — instead of closing its channels and waiting for the coins on-chain. The wallet shows the amount, both fees and what stays behind before anything is sent; until the on-chain transaction that creates the new channel has its first confirmation, the wallet user is trusting the new provider with that balance, and the wallet says so on the same screen. Where a balance cannot be moved the wallet says why and offers the plain switch (the channels close, the balance returns on-chain). Each provider's signed record states its fees, its channel limits, the confirmations it asks for on a channel the wallet funds, whether it runs a watchtower, and which of its connections pass through Cloudflare. The wallet checks that signature itself (since page v1179, engine v392): a record that does not match its provider's key, an older signed record than the one the wallet holds, and an unsigned record from a registry that signs are not used. The protocol and the registry live in [dav1dpgit/LIJOX](https://github.com/dav1dpgit/LIJOX); the LSP side in [dav1dpgit/lijox-lnd-adapter](https://github.com/dav1dpgit/lijox-lnd-adapter).
- **Always-on lives at the LSP; control stays in the wallet.** The LSP holds inbound payments while the phone is offline (registered payment hashes; preimages never leave the device) and cannot claim them; it wakes the phone with a push. Keys never leave the device.
- **You choose the route to your provider.** A provider may offer a direct connection (TLS ends on the operator's own machine) and a Cloudflare connection (Cloudflare's servers open the encryption and see what passes). Settings → Privacy → Network → Reach: *Directly when possible* (the default), *Never through Cloudflare*, or *Through Cloudflare first*. The same choice decides which of the registry's two addresses the wallet uses first, and where app updates are downloaded from.
- **Requests to the provider travel inside the Lightning connection.** A wallet's payments and channel messages always did. Since pages v1158 to v1175 its other requests to its provider do too, where the provider's adapter (0.137.0 or later) serves them there: the routes for a send, receiving and channel requests, the requests that move money (each with a request id: the provider carries a request out once, and a wallet that got no answer asks what became of it), and the checks a wallet makes before it connects (inside a short connection under a one-time key). They are encrypted to the provider's node key, and the connection's key is the proof of who asks. A provider on an older release gets them as web requests, as before. When a start's checks go as web requests at a provider that takes them inside, the wallet says so, and the provider's adapter (0.146.0) tells its operator of every such request.
- **Silent payments (BIP-352), both ways.** An `sp1q…` destination in the on-chain send pays a one-time taproot output derived from the wallet's own inputs; the BIP's test vectors run in the native test step. Receiving is built too: the wallet shows one reusable `sp1q…` address and finds its payments on the phone — the provider serves a per-block index of the transactions' tweaks, and the wallet does the scan-key arithmetic on the device (the scan key never leaves it) against the same block filters its on-chain walk reads. Coins received that way are the one thing a plain BIP84 wallet cannot recover from the 12 words alone, so the Black start kit carries a pre-signed sweep for each of them to the wallet's own m/84 address; receiving is on only while the chosen provider serves the index.
- **Mix: coinjoin with no coordinator.** Pools built on the public joinstr v2 code over Nostr. A provider keeps the waiting list and relays the pool's messages; a pool's payout goes through another provider, never the wallet's own. The changes made to the public joinstr code are in [docs/joinstr-patches.md](docs/joinstr-patches.md).
- **A watchtower, if you want one.** Settings → Privacy → Device → Watchtower (off by default): the wallet hands its penalty transactions, encrypted, to the watchtowers of other providers — two a channel when two offer one, never the channel's own provider — so an old channel state published while the phone is away is answered. The duties are in [docs/lijox-watch-standard-r2.md](docs/lijox-watch-standard-r2.md).
- **Also built:** Nostr Wallet Connect (the provider keeps the requests for a sleeping phone and cannot read them) and receiving zaps (off unless turned on: Settings → Privacy → LSP); Push Key (lock sats in your own channel and text the key; whoever opens it with a wallet takes them, and unclaimed they come back); delegated spends (a chit: a set amount a no-coiner can spend for you); Register mode for shops; paying an on-chain address from the Lightning balance through the provider; Subscriptions (a merchant's plan the wallet user agrees to; nothing is sent automatically).
- **A static site plus WASM.** No app store, no account. It runs offline once installed (a read-only room with the last known state).

## Read this before funding: what is true today

**One operator is still nearly every counterparty.** Three LSPs are registered: two are run by the wallet's author, and one, since 2026-11-19, by an independent operator. The registry, the default chain-data server and the backup host are the author's. Provider choice is real in the protocol and still thin in practice. This is a single point of failure for liveness (payments, channel opens, backups), not for custody: the wallet's channel state and keys are on the device, closes pay the device's own addresses, and a silent wallet's channel is force-closed by the LSP's lease timer after 60 days, which returns its balance to its m/84 address without any action by the user.

**A website can serve different code tomorrow.** That is true of every browser wallet and this one does not escape it. What exists against it:

- The engine and the page are built by the CI workflow in this repository from this source; every release's hashes are in [docs/releases.md](docs/releases.md) and [docs/reproducible-build.md](docs/reproducible-build.md) says how to compare the served files to them.
- Since 2026-10-21 lightninginajar.xyz is served from the author's own node, through a relay that passes the encrypted connection on without opening it. The files served are the repository's bytes: no edge rewrites them and no line is added. Cloudflare still answers the domain's DNS and keeps a copy of the same files; under *Directly when possible* an update file that fails at lightninginajar.xyz is taken from that copy, and every file from the copy is checked against the sha256 list in the service worker fetched from lightninginajar.xyz itself — a file that does not match is dropped. *Never through Cloudflare* downloads from lightninginajar.xyz only.
- **You can pin a build.** Settings → Functions → Updates → *Ask me*: the service worker then serves the installed build cache-first and a new build waits until you tap the update card. Under *Automatic* (the default) the wallet takes each new build on its next online open.
- The page's Content-Security-Policy allows only same-origin scripts and the page's own inline blocks by sha256 — no inline handlers, no `eval`. HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer` and a camera-only `Permissions-Policy` are set (`lij-pwa/frontend/_headers`).

**LDK is patched.** The engine builds against `lightning` 0.2.7 (since engine v375, 2026-11-17; 0.2.6 from engine v241) with 20 files changed, +833/−38 lines (as of engine v394, 2026-11-26): five files with behavioural changes; one read-only field and the two test constructors that set it (two files); three test-only files (two added with v376, one with v394), which compile into no build of the engine; and ten files of wasm32 clock substitutions (nine sources and the Cargo.toml line that pulls the browser clock in). Nobody independent has reviewed those lines yet. The full diff, with the purpose of every hunk, is [docs/ldk-patches.md](docs/ldk-patches.md). The behavioural changes are the cooperative-close fee floor, read-only accessors in the channel monitor, one boot-time hold that stops a pending cooperative close being double-spent by the holder commitment, a sweeper guard, the re-exposed `force_close_without_broadcasting_txn` (removed upstream in 0.1; needed for the stale-state abandon, which must never broadcast), since v393 one more read-only accessor in the channel monitor (the delay on the wallet's own output after a close by force), and, since v376, one timing rule: the wallet waits 4,032 blocks past the expiry of an HTLC it sent itself, not 3, before it goes on-chain over it (a broadcast delayed, none added). Commitment, revocation and penalty logic are upstream's; that timing rule is the only change to HTLC handling.

**Browser storage is fragile.** iOS can evict an installed web app's storage; "clear browsing data" wipes it. The 12 words recover on-chain funds; channel balances need the channel state. Keep the encrypted cloud backup on (Settings → Privacy → Cloud) and keep a downloaded copy (Settings → Safety → Backups → Save backup to device). Loading an older copy is the dangerous case: a phone that connects with a channel state older than its provider's makes the provider's LND close that channel by force. Since page v1152 a phone that knows it is behind is not offered a connection: it can catch up or close on purpose. Since page v1155 it also states its channel state to its provider, signed, before every connection; a provider on adapter 0.136.0 or later keeps the highest state each wallet has stated and gives no pass to a phone that states an older one, and that phone does not connect. What each recovery path can and cannot do is in [docs/recovery-classes.md](docs/recovery-classes.md) and [docs/recovery-outcomes.md](docs/recovery-outcomes.md).

**If the infrastructure disappears.** With the device and its state: the wallet force-closes its own channels and sweeps. With only the 12 words: the encrypted state copy at the backup host restores channels; if that too is gone, the LSP's lease timer closes a silent wallet's channels to its m/84 address within 60 days; and the Black start kit (Settings → Safety → Backups → Black start) is a pre-signed close-and-collect — and, for silent-payment coins, a pre-signed sweep — for the case where every party is gone. The encrypted kit is also kept with the LIJOX providers and on Nostr relays, so https://lightninginajar.xyz/recover can rebuild it from the 12 words alone, and each provider's adapter serves the same `/recover` page for when lightninginajar.xyz does not open. The standard is [docs/black-start-standard.md](docs/black-start-standard.md).

**Everything here is new.** The wallet domain is months old, there is no audit and no community history. Fund it with an amount whose loss you accept while that is so.

## Layout

```
lij/                 the engine: lij-core (wallet logic), lij-wasm (the wasm-bindgen surface),
                     patches/lightning (LDK 0.2.7 + the patch set), vendor/ (all crates, offline build)
lij-pwa/frontend/    the site and the wallet page, sw.js, styles, _headers (CSP), pkg/ (CI-built engine),
                     recover/ (the Black start page)
ops/frontend/        lij_csp.py (writes the CSP hashes at cut time), sw_stamp.py (the service worker's
                     file hashes), the handler-conversion test
ops/joinstr/         the gate for the joinstr v2 code the Mix builds on
ops/lij-tier2-filters.py   the chain-data endpoint (headers / BIP158 filters / blocks off bitcoind)
ops/lij-sp-index.py        the silent-payment tweak index, and its tests beside it
.github/workflows/   lij-build (engine + page, deploy branch, hashes), lij-engine-build, joinstr-gate,
                     lij-ops-tests, recover-canary, tag-release, gitlab-mirror
docs/                design records and standards: recovery, Black start, the watch and copy-guard
                     standards, the static-address model, delegation, closes, the LDK and joinstr patches
```

## Building

See [docs/reproducible-build.md](docs/reproducible-build.md). Short form: Rust 1.90.0 stable (pinned in `lij/rust-toolchain.toml`), `wasm-pack build --release --target web --out-dir ../../lij-pwa/frontend/pkg lij-wasm` inside `lij/`, crates vendored. The page is plain HTML/JS with no build step; the CSP hash line is written by `ops/frontend/lij_csp.py`.
